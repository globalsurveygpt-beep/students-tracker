# План работ: веб-приложение учёта посещаемости студентов

Срок: 5 дней = 3 рабочих + 2 запасных. Запасные дни — для печатного документа, скриптов запуска и репетиции защиты, а не для новых функций.

## 1. Зафиксированные решения

| Область | Решение |
|---|---|
| Backend | C#, ASP.NET Core 10 (.NET 10 LTS), Minimal API или контроллеры (выбрать один стиль в спеке и не смешивать) |
| ORM | EF Core 10 + Npgsql (провайдер для EF Core 10), миграции |
| БД | PostgreSQL 18 (установлен у владельца, защита на его компьютере) |
| Frontend | Статичные HTML/CSS/JS в `wwwroot`, без фреймворков, `fetch` к REST API того же origin |
| Авторизация | Cookie-аутентификация, хеш пароля через `PasswordHasher`, роли `admin` / `teacher` / `student` |
| Учётные записи | Создаёт админ: логин + временный пароль. Свободной регистрации и кодов приглашения нет |
| Студент | Только чтение своей посещаемости; права проверяются на сервере |
| Дизайн | Единый источник: `mockups/!DESIGN_TOKENS.html` (цвета, шрифты, радиусы, отступы, SVG-иконки) |
| Шрифты | Локально в `wwwroot/fonts`, без CDN (защита может быть без интернета) |
| Презентация | Не нужна |

Чего не делаем (против оверинжиниринга): микросервисы, CQRS, репозитории поверх EF, SPA-фреймворки, JWT, Docker, принудительная смена пароля при первом входе.

## 2. Документы (папка `docs/`)

| Файл | Назначение | Формат |
|---|---|---|
| `PLAN.md` | Этот план | Markdown |
| `SPEC.md` | Спецификация для сборки проекта: требования, роли, сценарии, API, ERD (Mermaid), версии, список ошибок и мер защиты | Markdown |
| `DB_STRUCTURE.xlsx` | Один лист, секции по таблицам: колонки, типы, ключи, ограничения, связи | Excel |
| `ERD.png` / `ERD.svg` | ERD для печатного документа (Mermaid не вставляется в Word) | Изображение |
| `RUN.md` | Запуск проекта с нуля в три команды, восстановление БД | Markdown |
| `PROJECT_DOC.docx` | Печатный документ для учителя (структура ниже, оформление — по требованиям учителя) | Word |

Вне `docs/`: `mockups/` (макеты и `!DESIGN_TOKENS.html`), `src/` (код), `db/` (скрипты схемы, сид, дамп).

## 3. Модель данных (предварительно, уточняется в SPEC.md)

- `users` — логин, хеш пароля, роль, активность.
- `groups` — название, год.
- `students` — ФИО, группа, ссылка на `users` (nullable, уникальная).
- `subjects` — название.
- `lessons` — дата (`date`), номер пары, предмет, группа, преподаватель.
- `attendance` — урок, студент, статус (`present` / `absent` / `excused` / `late`), примечание. Уникальность пары (урок, студент).

Заранее учтённые ошибки: даты урока как `date` без часового пояса; уникальность отметки; запрет каскадного удаления студента с историей (мягкое удаление или запрет); хеширование паролей; строка подключения вне git; воспроизводимые миграции; серверная проверка прав по роли.

## 4. Расписание

### День 1 — основа и дизайн (блокер: принятие макетов владельцем)
1. SPEC.md с ERD, перечнем экранов и API (2 ч).
2. DB_STRUCTURE.xlsx (1 ч).
3. `!DESIGN_TOKENS.html`: тёмная/светлая темы, акцент, шрифты, радиусы, шкала отступов, иконки SVG (2 ч).
4. Макеты в `mockups/`: вход, группы, студенты, отметка посещаемости, отчёт, кабинет студента (3 ч).
5. **Принятие макетов владельцем.** Без него код фронта не пишется.

### День 2 — база и бэкенд
1. Каркас решения, подключение к PostgreSQL, миграции, сид-данные (2 ч).
2. Авторизация, роли, политики доступа, смена пароля (2 ч).
3. CRUD: группы, студенты (с созданием учётной записи), предметы, уроки (3 ч).
4. Отметка посещаемости, отчёты (процент по студенту и по группе), поиск (2 ч).
5. Единый формат ошибок, валидация, проверка прав студента.

### День 3 — фронтенд и интеграция
1. Базовые стили из токенов, шаблон страниц, обёртка над `fetch` (2 ч).
2. Страницы по принятым макетам (4 ч).
3. Адаптивность, пустые состояния, ошибки (1 ч).
4. Сквозная проверка трёх ролей (1 ч).

### День 4 — запас: печатный документ
Введение, главы 1–4, заключение, литература, приложения; ERD и диаграммы As-Is / To-Be (BPMN или IDEF0); листинги ключевых функций; экономика (затраты на разработку, эффект по времени преподавателя). Оформление — по требованиям учителя (**требования нужны не позже начала дня 3**).

### День 5 — запас: стабилизация
Скрипт запуска и восстановления БД (`RUN.md`), проверка на чистой установке, исправления, репетиция защиты (архитектура, демонстрация, ответы на вопросы), печать.

## 5. Структура печатного документа (по требованиям задания)

Титульный лист → оглавление → введение (актуальность, объект, предмет, цель, задачи) → Глава 1 (теория, аналоги, методологии) → Глава 2 (характеристика объекта, As-Is, проблемы, To-Be) → Глава 3 (стек, архитектура, ERD, модули, листинги) → Глава 4 (экономика) → заключение → список литературы → приложения.

## 7. Риски

- Задержка принятия макетов сдвигает всё остальное.
- Запасные дни съедаются документом; новые функции в них не добавляются.
- Сбой окружения на защите: нужен проверенный сценарий восстановления БД с нуля.
